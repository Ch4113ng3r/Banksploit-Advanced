# CTF Integrity Flaws — To Treat Later

These are known design weaknesses that allow unintended shortcuts or cross-vulnerability flag leakage. They don't break the app but undermine CTF fairness.

---

## 1. Flag Submission Accepts Any Vuln's Flag Without Proof-of-Work

**Endpoint:** `POST /api/v1/training/submit-flag`

**The problem:** The submission API takes a bare flag string and auto-detects which vulnerability it belongs to by looping all 10 vulns and comparing HMACs. There's no requirement to:
- Specify which vulnerability you're claiming credit for
- Provide a nonce/token proving you actually triggered the exploit
- Demonstrate the exploit path (e.g. a session breadcrumb set by the vulnerable endpoint)

**Why it matters:** If a user obtains a flag through an unintended channel (e.g. shoulder-surfing, a leaked screenshot, or a cross-vuln leak we missed), they can submit it and get credit with no questions asked. The system can't distinguish "I exploited this" from "I got this flag some other way."

**Potential fix:** Require a `vuln_key` in the submission request AND a proof token — a short-lived nonce generated by the vulnerable endpoint at the moment of exploitation. The submission endpoint would verify both the flag AND the nonce.

## 2. Source Code Exposure → Hardcoded Secret → Forge All Flags

**The problem:** Two existing vulnerabilities can read `src/core/Flags.php`:

- **G11 (LFI):** `?page=../../../../core/Flags` → PHP includes/reads the file directly
- **G8 (Path Traversal):** The CSV export endpoint can stream arbitrary files from disk

Additionally, the **code viewer** at `/training/code` may expose Flags.php as part of its "view vulnerable vs secure source" feature.

**What the attacker learns from Flags.php:**
```php
$hash = hash_hmac('sha256', "{$userId}:{$vulnKey}", self::secret());
$short = strtoupper(substr($hash, 0, 12));
return "BANKSPLOIT{{$short}}";
```
Plus the fallback secret: `'banksploit_ctf_flag_secret_2024'`

**The exploit chain:**
1. Read Flags.php via LFI, path traversal, or code viewer
2. See the HMAC algorithm + fallback secret
3. Know your own userId (from session/JWT/account page)
4. Know all vulnKey values (visible on the /lab page: `auth.l11`, `auth.g1`, etc.)
5. Compute all 10 flags locally → submit → full 2300 points without exploiting anything

**Why it's dangerous:** This is a "god-mode" chain — one file read defeats the entire CTF.

**Potential fixes:**
- Remove the hardcoded fallback from Flags.php (require env var or fail hard)
- Move the secret into a file outside the web root (not reachable by LFI/path traversal)
- Exclude Flags.php from the code viewer's allowed file list
- Load the secret into memory at boot and clear it from any file on disk

## 3. ~~FLAG_SECRET Hardcoded Fallback in Flags.php~~ ✅ FIXED

**Fixed on:** 2026-07-03

**What was done:**
- Removed the hardcoded fallback `'banksploit_ctf_flag_secret_2024'` from `Flags.php`
- `Flags::secret()` now throws `RuntimeException` if `FLAG_SECRET` env var is missing
- `start.sh` generates a random 64-char hex secret on first run, stores it in `.local/flag_secret`
- `.local/` is in `.gitignore` — secret never enters source control
- Reading `Flags.php` via LFI/path traversal no longer reveals any secret value
