Understanding the Attack Vectors

⚡ End-to-End Compromise — Just Like Real Attackers

This lab is designed to simulate a full attack chain — the same sequential compromise flow that real-world attackers use to go from zero access to owning the server.

🎯 The Kill Chain: Gain initial access → Escalate privileges → Move laterally → Access sensitive data → Achieve remote code execution. Each vulnerability you exploit unlocks the next step in this chain. By the end, you will have gone from an unauthenticated outsider to executing arbitrary commands on the server — a complete compromise achieved purely by chaining the embedded vulnerabilities in sequence.
— Real-World Attack Simulation

Think like an attacker: start by getting in (authentication bypass), explore what you can reach (IDOR, data access), escalate your privileges (JWT forgery), and ultimately own the server (command injection). This is how breaches happen in the wild.

🔓 SQL Injection (SQLi)

What it is: SQL injection occurs when user input is directly concatenated into SQL queries without sanitization. An attacker can inject SQL code to manipulate query logic, bypass authentication, or extract arbitrary data from the database.

The Vulnerability

// Vulnerable Code
$query = "SELECT * FROM users WHERE customer_id = '" . $_POST['id'] . "' AND password = '" . $_POST['pass'] . "'";

🎯 Part 1: Authentication Bypass

The simplest SQLi attack comments out the password check, allowing login without knowing credentials.

  • Identify where user input is used in the SQL query
  • Inject a single quote ' to break out of the string
  • Use SQL comment syntax (typically #) to comment out the rest
  • The resulting query becomes: SELECT * FROM users WHERE customer_id = 'YOUR_INPUT' #
  • The password check is effectively removed

🎯 Part 2: Data Extraction Using UNION SELECT

Beyond bypass, SQLi can extract any data from the database. This requires understanding the query structure:

Step 1️⃣: Determine Column Count

The original query returns a certain number of columns. Use ORDER BY to find it:

  • Try injecting ORDER BY 1 # (no error = 1+ columns)
  • Try injecting ORDER BY 2 # (no error = 2+ columns)
  • Try injecting ORDER BY 3 # (no error = 3+ columns)
  • Keep increasing until you get an error
  • The last successful number is your column count
  • Example: If ORDER BY 5 # works but ORDER BY 6 # fails, the query returns 5 columns

Step 2️⃣: Extract Data With UNION SELECT

Once you know the column count, use UNION SELECT to append your own query:

  • Construct a UNION SELECT with the same number of columns
  • Place values in positions where they will be displayed
  • Example: If the original returns 3 columns: UNION SELECT 1, 2, 3 #
  • The numbers (or strings) you select appear in the output
  • This confirms which columns are displayed to the user

Step 3️⃣: Discover Table Names

Databases store metadata about their own structure. Explore what's available using information schema queries:

// MySQL: List all tables
UNION SELECT table_name, 2, 3 FROM information_schema.tables #

// MySQL: List columns for a specific table
UNION SELECT column_name, 2, 3 FROM information_schema.columns WHERE table_name = 'table_name_here' #
  • Table names are stored in information_schema.tables
  • Column names are stored in information_schema.columns
  • You can query these metadata tables just like any other table
  • Start by discovering what tables exist, then explore their columns

Step 4️⃣: Extract Sensitive Data

Once you know table and column names, extract the data you want:

// Generic example
UNION SELECT column1, column2, column3 FROM table_name #
  • Replace column1, column2, column3 with actual column names
  • Replace table_name with the actual table
  • The query executes and returns data directly in the page

💻 OS Command Injection

What it is: When applications pass user input to system shell commands (exec, system, passthru), metacharacters can break out of the intended command and execute arbitrary OS code.

Attack Flow

// Vulnerable Code
exec("ping " . $_GET['host']); // What could go wrong?

Exploitation

  • Enter a legitimate hostname to confirm the endpoint works
  • Use shell metacharacters like ; or | to chain commands
  • Example: 8.8.8.8 ; ls /tmp executes both the ping AND lists directory contents
  • The flag is written to a file you can then read
"Command injection is trusting the user to stay in their lane. The shell doesn't care about lanes."
— Systems Administrator

🔑 JWT Algorithm Confusion

What it is: JSON Web Tokens (JWT) are cryptographically signed claims that encode user information. If a server accepts the 'none' algorithm, an attacker can forge tokens with arbitrary claims.

How JWT Works

  • JWT consists of three parts: Header.Payload.Signature
  • Server signs the token with a secret to verify authenticity
  • If the signature is valid, the server trusts the claims inside
  • The 'none' algorithm is meant for debugging—it signs nothing

The Attack

Use jwt.io to:

  • Decode an existing token to see its structure
  • Change the algorithm to 'none' in the header
  • Modify claims (like admin: true or role: 'superadmin')
  • Clear the signature (leave it blank)
  • Copy the forged token and use it in the application
"Trust, but verify. If you're verifying signatures, make sure you're actually verifying them—not just checking that something claims to be signed."
— Cryptography Researcher

📊 IDOR (Insecure Direct Object Reference)

What it is: When applications use client-supplied identifiers to fetch records without verifying ownership. Changing the ID parameter exposes other users' data.

Two Flavors in This Lab

  • Statements IDOR: Manipulate the URL parameters on the statements page to view other users' transaction history
  • Transfer IDOR: Modify the source account details in the transfer request to move money from accounts you don't own (client-side protections are cosmetic)

The Security Lesson

Client-side restrictions (disabled form fields, hidden inputs, readonly attributes) are cosmetic only. The server must verify ownership on every single request. Never trust the client.

"The browser is the attacker's computer. Never trust anything the client sends. The server is the only thing you control."
— Backend Security Principal

🚀 Brute Force & Sensitive Data Exposure

Brute Force: When systems use short numeric codes (like 4-digit OTPs) without rate limiting, an attacker can try all 10,000 combinations in seconds.

Sensitive Data Exposure: Developers sometimes leave debug information in production code—OTP values in JavaScript, API keys in network responses, secrets in HTML comments.

"Debug mode must never ship to production. Every console.log could be a security breach."
— Code Review Expert

💡 Pro Tips for Success

🌐 Browser-Only Challenge

This CTF is designed to be exploited using only a web browser. You will not need additional tools, command-line utilities, or specialized security software. Everything you need is already available in your browser.

  • Copilot is OK: Use AI assistants to understand concepts and explore techniques, but aim to understand the exploit yourself—don't just copy-paste payloads blindly.
  • Read Error Messages: Error messages often hint at what went wrong. Database errors, stack traces, and API responses are your friends.
  • Document Your Process: Note which vulnerability you exploited and how. This helps you learn and teaches others.
  • Time Management: Prioritize easier vulnerabilities first to rack up quick points, then tackle the harder ones.
  • Ask for Hints: If stuck, hints will be released after a few minutes. Check back regularly!

How Hints Work

💬 Hint Side Panel

When the instructor enables a hint for a vulnerability, a floating panel appears on the right side of your screen. It contains strategic guidance to nudge you in the right direction without spoiling the exploit.

🎯 Per-Vulnerability

Each vulnerability has one comprehensive hint that can be enabled or disabled by the instructor. When you're on a page with an active vulnerability, its hint (if enabled) will be visible.

⏰ Instructor-Controlled Release

The instructor controls when hints appear. If you're stuck, a hint may become available after a few minutes. Keep an eye on the right side of the screen!

When Hints Appear

  • On Vulnerable Pages: When you navigate to a page with a vulnerable function, relevant hints appear in the side panel (if enabled).
  • Instructor-Released: The instructor may enable hints at strategic times—typically after several minutes of attempts or when many participants are stuck.
  • Dismissible: You can close the hint panel by clicking the ✕ button. It may reappear when you navigate to a new page or refresh.
  • On Multiple Pages: Different pages may have different hints. The login page hints differ from the transfers page hints, etc.

How to Use Hints Effectively

  • Read Carefully: Hints are intentionally vague to avoid spoiling the discovery process. Read between the lines.
  • First 5 minutes: Try to solve it yourself. Most vulnerabilities are discoverable with creative thinking.
  • 5+ minutes stuck: Check if a hint has appeared. If not, the instructor may release it soon.
  • Still stuck? A hint will guide you toward the vulnerable parameter, input method, or tool you need. The exact payload is still on you to discover.
