Session Objective

Give technology leaders first-hand experience of how ordinary design assumptions become attack paths, then connect those moments to the leadership decisions that reduce business risk.

Through a series of controlled demonstrations, you will experience how an attacker can move from a seemingly minor weakness to compromising customer data and application infrastructure. The objective is to show how attack paths are created across multiple control domains, reinforcing why AppSec, IAM, Cyber Operations, and Penetration Testing must operate as an integrated defence capability, particularly in an AI-enabled threat landscape.

Sound Familiar?

"Can we lower the severity from High to Medium? It's blocking our release and it doesn't really seem high risk."

Severity is based on exploitability and impact — not your sprint deadline. The vulnerability doesn't care about your release date.

"This is an internal API — no one outside can reach it. Why do you want a pen test for this?"

Many serious incidents expand through internal lateral movement after the first foothold. “Internal” is a trust boundary to defend, not proof of safety.

"Only a few individuals in my team have access to this resource and they are trusted."

Insider threat isn't about trust — it's about blast radius when credentials are compromised. An attacker with a stolen session IS your trusted employee.

"Our gateway has all checks in place. We don't need to fix the code — it's additional burden."

A gateway is a seatbelt, not a replacement for brakes. What happens when someone bypasses it?

"We'll fix it in the next release. Let this one go to production."

When is the next release? Is there an owner? A tracking ticket? "Next release" without a date is "never."

"We've been running this for 3 years and nobody has exploited it."

That you know of. Absence of detection is not absence of exploitation. You're about to see a data breach that leaves no trace.

"Can you just whitelist this finding in the scanner so it stops blocking the pipeline?"

Silencing the alarm doesn't put out the fire. If it's a false positive, document why. If it's real, suppressing it is accepting risk without the paperwork.

"The vendor said it's secure — they gave us a compliance certificate."

A compliance certificate says the vendor met a checklist at a point in time. It says nothing about your integration, your configuration, or their next update.

"We're running our application over HTTPS — that means it's secure."

HTTPS encrypts the transport. It doesn't validate your inputs, check your authorization logic, or stop SQL injection. A locked delivery truck doesn't guarantee what's inside is safe.

By the end of this session, you will have the evidence and the language to answer every one of these.

The Security Mindset

The difference between a secure application and a vulnerable one is rarely the technology. It's whether someone asked "what could go wrong?" before shipping.

What the Builder AssumesWhat the Attacker Sees
"The user will enter a Customer ID""What if I enter SQL code instead?"
"This field is disabled — they can't change it""Disabled in the browser. What about the raw HTTP request?"
"Only authenticated users reach this page""Authenticated, yes. But authorized for THIS data?"
"We're using HTTPS and a gateway""The injection happens INSIDE the encrypted tunnel."
"The admin panel URL isn't documented anywhere""I'll try /admin, /manage, /dashboard — found it in 5 seconds."

Sounds reasonable, right? These are the assumptions developers make every day.

The builder thinks about what the system should do. The attacker thinks about what it could do.

🔴 Demo 1 G1 • CWE-89 • OWASP A03:2021

SQL Injection — Login Bypass

"We're going to log in as anyone, without their password."

How Login Normally Works

You type your Customer ID and password. The server checks the database.

SELECT * FROM users
WHERE customer_id = 'BS100234'
  AND password_md5 = '5f4dcc3b5aa765d...'

If the Customer ID and password match a row in the database, you're in. Simple and correct — as long as the input is handled safely.

The Attack

What we type

Customer ID:

BS100234' --  

Password:

anything

What the server executes

SELECT * FROM users
WHERE customer_id = 'BS100234' -- '
  AND password_md5 = '...'

The -- turns the password check into a comment. The database never evaluates it. We're in.

The Vulnerable Code

From the actual login handler — the user's input is concatenated directly into the SQL string.

// login_vuln.php — Level 0: classic SQL injection
$sql = "SELECT id, customer_id, name, role FROM users "
     . "WHERE customer_id = '" . $cid . "' "
     . "AND password_md5 = '" . md5($password) . "' LIMIT 1";

$result = $pdo->query($sql);

$cid — User-supplied value pasted directly into SQL. Whatever the user types becomes part of the query. The attacker controls the database logic.

This bank's entire authentication just collapsed because of one missing function call.

SQL injection is a 25-year-old vulnerability class.
It's still in the OWASP Top 10.
It's still being written today.

The Fix — And Why It Works

// login_secure.php — parameterized query
$stmt = $pdo->prepare(
    'SELECT id, customer_id, name, role,
            password_hash
       FROM users
       WHERE customer_id = :cid
       LIMIT 1'
);
$stmt->execute([':cid' => $customerId]);

// + password_verify() replaces MD5

Why this works

Step 1: The database receives the SQL template and compiles it into an execution plan. The query structure is locked.

Step 2: User data (:cid) is sent separately and bound to the placeholder as a literal value.

Step 3: The data is never parsed as SQL. Even if the user types ' OR 1=1 --, the database treats the entire string as a value to search for — not as code to execute.

Think of a printed form with blank fields. The form's structure is fixed. Whatever you write in the blanks is content — you can't rewrite the form itself.

Who Should Have Caught This?

Application Security

SAST scanners flag string concatenation in SQL queries automatically. This is one of the most well-known static analysis rules in existence.

Code review catches $pdo->query($sql) with variable interpolation. A single reviewer asking "where does this variable come from?" prevents this vulnerability entirely.

Secure coding standards mandate parameterized queries. The pattern is documented in every language, every framework, every security guide written in the last two decades.

"This is a 25-year-old vulnerability. Automated tools detect it.
The question is: does your SAST pipeline run before merge?"

🔴 Demo 2 SL1 • CWE-639 • OWASP A01:2021

IDOR — View Another Customer's Statements

"We're going to read another customer's financial history."

The Setup

1

We're logged in as Rahul Sharma. We navigate to the Statements page.

2

We notice the URL contains our account number:

/statements?account=50100100000001
3

We visit the Beneficiaries page. We can see other people's account numbers — that's normal, we pay them.

4

We see Priya Menon's account number: 50100100000002

The Attack

We change one number in the URL bar. That's the entire attack.

Before (my account)

/statements?account=50100100000001

After (Priya's account)

/statements?account=50100100000002

We press Enter. We can see all of Priya Menon's transactions.

The Vulnerable Code

// VULNERABLE: no ownership check
$stmt = $pdo->prepare(
    "SELECT ... FROM accounts a
       JOIN users u ON u.id = a.user_id
       WHERE a.account_number = :acct"
);
$stmt->execute([':acct' => $accountNumber]);

The query finds the account by number. It parameterises the input (no SQL injection). But it never checks whether the logged-in user owns that account. Any valid account number works for any user.

We just committed a data breach.
We didn't hack anything.
We changed a number in the URL.

No tools. No scripts. No technical knowledge.
Just a browser address bar.

The Fix

// SECURE: ownership check added
$stmt = $pdo->prepare(
    "SELECT ... FROM accounts a
       JOIN users u ON u.id = a.user_id
       WHERE a.account_number = :acct
       AND a.user_id = :uid"
);
$stmt->execute([':acct' => $accountNumber, ':uid' => $currentUserId]);

AND a.user_id = :uid — five words. That's the entire fix.

Why Automated Tools Miss This

This is OWASP #1: Broken Access Control — the most common web application vulnerability category in the world.

SAST tools may flag suspicious data flows or inconsistent checks, but they cannot reliably prove the intended authorisation policy without business context. SQL injection is a code pattern — string concatenation in queries. IDOR is a business logic flaw. A scanner can't know that this page should check ownership but that page is intentionally public. It requires understanding the application's authorization context.

IAM designed the access rules. The system authenticates correctly — it knows who you are. But knowing who you are is not the same as enforcing what you're allowed to see.

Penetration Testing is the primary detection method. A pen tester's first instinct on any URL with an ID parameter: "What happens if I change this?"

"The authorization policy existed. The code didn't enforce it.
No scanner can tell you that — only a human reviewing the logic."

🔴 Demo 3 G9 • CWE-78 • OWASP A03:2021

Command Injection — Server Takeover

"We're going to take control of the server. From a PDF download button."

The Normal Flow

The Statements page has an "Export PDF" feature. It takes a filename and passes it to a command-line tool that generates the PDF.

// The intended command:
wkhtmltopdf /tmp/source.html /tmp/statement.pdf

The filename — statement.pdf — comes from the request. The developer assumed it would always be a simple filename. It isn't.

Step 1: Discovery

We change the filename to include a shell metacharacter:

filename = x.pdf;ls;

The semicolon ends the PDF command and starts a new one. The server executes:

wkhtmltopdf /tmp/src.html /tmp/x.pdf;ls;

Instead of a PDF, the server returns a directory listing. We can see every file on the server's temp directory — including a suspicious file called flag_g9_1.txt.

Step 2: Extraction

Now we read the flag file:

filename = x.pdf;cat /tmp/flag_g9_1.txt;

The server outputs the contents of the file. The flag appears in the response.

BANKSPLOIT{A8F3C21D9E0B}

"We just ran arbitrary commands on the server.
From a PDF download button. In a banking app."

The Vulnerable Code

// VULNERABLE: user-supplied filename concatenated into shell command
$cmd = "wkhtmltopdf $src {$tmpDir}/" . $filename . " 2>&1";

$filename — whatever the user sends in the request becomes part of the command line. Shell metacharacters (; | ` $()) break out of the intended command and execute whatever the attacker wants.

The Fix — Two Layers

Primary: Input Validation (Whitelist)

// BEST: only accept safe characters
if (!preg_match(
    '/^[a-zA-Z0-9._-]+$/',
    $filename
)) {
    throw new \InvalidArgumentException(
        'Invalid filename'
    );
}
// Letters, digits, dots, underscores,
// hyphens only — everything else rejected

Define what's allowed, reject everything else. The attack input x.pdf;ls; never reaches the shell — the semicolons fail the whitelist.

Secondary: Shell Escaping (Quick Fix)

// GOOD: escape shell arguments
$cmd = 'wkhtmltopdf '
  . escapeshellarg($src)
  . ' '
  . escapeshellarg($out)
  . ' 2>&1';

escapeshellarg() wraps the value in single quotes and escapes special characters. Good, but relies on the escaping function being bug-free.

Whitelist first. Escape as a safety net. Both together is best.

Defence in Depth

When Application Security misses a command injection, which other layers should catch it?

🛡️ Cyber Operations / SOC

Should detect unusual process execution — cat, ls, whoami spawned by a web server process is a red flag. Behavioural anomaly detection catches what code review missed.

🏗️ Infrastructure Security

Principle of least privilege. The web process shouldn't have read access to arbitrary files. Container sandboxing, restricted shells, and process isolation limit blast radius.

"Security is layers. When one fails, the next should catch it."

🟡 Exercise 1 L11 • CWE-200 • OWASP A04:2021 • 100 pts

Find the OTP Without a Phone

You've logged in with the correct Customer ID and password. You're on the OTP verification screen. You don't have the victim's phone.

Can you still get in?

⏱️ 8 minutes. Work in pairs if you'd like.

Instructions

1

You're on the OTP verification page. The page is waiting for a 4-digit code.

2

Open DevTools: press F12 (Windows) or Cmd+Opt+I (Mac).

3

Explore. The OTP is somewhere your browser has already downloaded. You don't need to make any new requests.

The attacker's superpower isn't hacking — it's reading what the application is already sending.

Hints (if you're stuck)

Hint 1: Go to the Sources tab in DevTools.

Hint 2: Look at the JavaScript files the page loaded. There's one called otp-validation.js.

Hint 3: Open it. Search for SESSION_DATA. The OTP is right there — along with the CTF flag.

The Answer

// otp-validation.js — loaded by the OTP page
var SESSION_DATA = {
    "_t":    "otp",
    "_v":    "2.1.4",
    "_otp":  "7241",       // ← THE OTP
    "_flag": "BANKSPLOIT{...}", // ← THE CTF FLAG
    "_sid":  "abc123",
    "_exp":  1719500000
};

A developer left debug data in a JavaScript file that gets shipped to every user's browser. The OTP — a secret that should only exist server-side — is embedded in client-side code.

Client-side code is not secret.

Everything sent to the browser is visible to the user. JavaScript files, hidden form fields, API responses, cookies — all of it is readable.

Secrets belong on the server. Never in JavaScript.

🟡 Exercise 2 L1 • CWE-639 • OWASP A01:2021 • 300 pts

Transfer Money from Someone Else's Account

The "From Account" field is greyed out. You can only transfer from your own account.

Or can you?

⏱️ 10 minutes.

Instructions

1

Go to the Transfer page. Notice the "From Account" field is disabled (greyed out).

2

Right-click the greyed-out field. Click Inspect Element.

3

Look at the HTML. There's a <input type="hidden" name="from_account_id"> that carries the actual value the server reads.

4

Change its value to another user's account ID. Complete the transfer wizard.

Think about it: the UI says you can't change this field. But who enforces that — the browser, or the server?

The Answer

<!-- What the Transfer page renders -->
<select disabled class="...">
  <option>50100100000001 (Savings)</option>
</select>

<!-- The hidden input the server actually reads -->
<input type="hidden" name="from_account_id"
       value="1">  <!-- Change this to "4" -->

The disabled attribute is a UI hint to the browser. The hidden input is what the server reads. Change value "1" to "4" (another user's account), submit the form, and the transfer goes through. The server never checked ownership.

The developer thought a disabled form field was a security control.

It's a suggestion to the browser. The server must enforce it independently.

Client-side validation is UX.
Server-side validation is security.
They are not interchangeable.

You saw where assumptions become security risks.

Across these demos, the pattern was consistent: the application trusted something it should have verified.

01   Identity ≠ authorisation

A logged-in user is not automatically entitled to every account or record.

ASK  Do we verify ownership and permission for the exact object at every sensitive action?

EXPECT  Server-side, per-object authorisation checks; test with two distinct customer identities.

02   The client is not trusted

Anything sent to the browser can be inspected, copied or manipulated.

ASK  Are secrets, OTPs, debug values or security decisions reaching the client?

EXPECT  Keep secrets and security-critical decisions server-side; inspect shipped scripts and responses.

03   Input must remain data

User-controlled input must never change the instructions our systems execute.

ASK  Are we relying on filters — or structurally preventing input from changing a query?

EXPECT  Use parameterised queries; validate business rules; test hostile input on sensitive paths.

04   Workflows must be challenged

A feature can work correctly and still fail when steps, state or trust are manipulated.

ASK  Do we test only the happy path, or also skipped, repeated, reordered and abused journeys?

EXPECT  Threat-model end-to-end flows; test session transitions, recovery paths and negative scenarios.

Leadership’s role  —  Set the expectation • Fund the time • Assign owners • Track remediation • Verify the fix

When a High-Risk Finding Lands on Your Desk

Before raising an ORAC (Operational Risk Acceptance Certificate), ask these questions:

🛡️ Compensating Controls

"If we can't fix it now, what reduces the risk?"
WAF rules for injection, enhanced logging for IDOR, network segmentation for command injection, rate limiting for brute force.

📅 Fix Timeline

"What is the hard deadline to remediate?"
Risk acceptance without a fix date is risk ignorance. Set a date. Track it. Escalate if it slips.

💥 Exploitation Impact

"If this is exploited tomorrow, what's the blast radius?"
Financial loss? Regulatory penalty? Reputational damage? Customer data exposed? Quantify — don't guess.

🔍 Validation

"Has Pen Testing confirmed this is exploitable? Can SOC detect exploitation?"
Ask the security team to prove the risk. Then ask if monitoring can catch it live.

Risk acceptance is not risk ignorance.
Accept with controls, timelines, and accountability.

AI in Security

The Accelerant

AI as Attacker

Everything demonstrated in this session — the SQL injection payloads, the JWT forgery, the IDOR patterns, the command injection — an AI model can generate all of it from a single prompt.

What AI Can Do Today

Generate SQL injection payloads tailored to any login form. Craft JWT forgeries given a sample token. Enumerate IDOR patterns from API documentation. Write brute-force scripts in any language, in seconds.

What This Means

AI can lower the skill and time required to attempt familiar attacks, but successful exploitation still depends on access, context, validation and operational skill. The practical implication is greater attack volume and faster iteration.

The Bar Has Dropped to Zero

Prompt:

"Generate SQL injection payloads to bypass a login form that checks customer_id and password"

AI Output:

BS100234' --                 // Comment out password check
' OR 1=1 --                   // Tautology bypass
' UNION SELECT 1,2,3,4 --     // Column enumeration
admin'/*                       // Block comment variant

AI can accelerate payload design and testing, but its output must be authorised, validated and constrained. It does not remove the need for technical expertise.

AI as Defender

The same AI capabilities that enable attacks also power defence at unprecedented speed and scale.

SAST / DAST with AI

AI-assisted analysis can flag suspicious injection patterns, unsafe APIs, exposed client-side data and risky configurations. Business-logic and authorisation findings still require context and validation.

AI Code Review

Identifies client-trust anti-patterns, reviews pull requests for security regressions, suggests fixes with correct code. Scales security review to every commit, not just the ones a human has time to read.

Anomaly Detection

AI-based SOC tools flag unusual command execution from web processes, detect brute-force patterns across login endpoints, identify bulk data extraction from statement APIs.

Pen Test Triage

Prioritises findings by exploitability and business impact. Maps vulnerabilities to OWASP categories and CWEs automatically. Reduces triage time from days to hours.

AI Accelerates Both Sides Equally

Attackers

Lower barrier to entry. Automated payload generation. Faster reconnaissance. Wider target surface. Anyone with a prompt can attempt what once required years of expertise.

Defenders

Automated vulnerability detection. Continuous code review at scale. Real-time anomaly detection. Faster incident triage. Security testing on every commit, not just quarterly pen tests.

The difference is who adopts it first and uses it consistently.

What AI Still Cannot Do

AI is a powerful tool, but these require a human in the loop — today and for the foreseeable future.

🧠 Business Context

AI can flag a missing auth check but can't know if that page is intentionally public. Understanding the business requirement behind code is a human judgment call.

⚖️ Risk Acceptance Decisions

"We accept this risk for 90 days with compensating controls" — weighing business priorities, regulatory exposure, and customer trust. No model can own that decision.

🔍 Validating AI Output

AI hallucinates — it generates confident, plausible, and completely wrong security advice. Every AI recommendation must be validated by someone who knows the domain.

🚨 The 2 AM Judgment Call

When the alert fires: escalate or contain? Notify the regulator now or investigate first? Shut down the service or accept partial risk? Human decisions with human consequences.

🤝 Stakeholder Negotiation

Convincing a product team to delay a launch for a critical fix. Explaining risk to the board in non-technical language. AI can draft the memo — but can't have the conversation.

🏗️ Culture Building

Making developers want to write secure code. Creating an environment where reporting vulnerabilities is rewarded, not punished. Culture comes from leaders, not algorithms.

AI is a force multiplier for your security teams, not a replacement.

AI can find the SQL injection in milliseconds. But a human decided to skip the code review that would have caught it. AI can detect the brute-force in real time. But a human decided not to fund the SOC tooling.

It still takes a human to decide that security matters.
To fund the tools. To set the culture.
To respond when the alert fires at 2 AM.

🟢 Takeaways

Three Things to Remember

1

The code change may be small. Sustainable prevention is systemic.

Some individual code changes may be small, but safe remediation also requires regression testing, consistent enforcement, deployment assurance and verification. The technology existed for decades. What was missing was the awareness, the review process, the culture that makes developers ask: "what could go wrong if someone did this on purpose?"

2

AI has lowered the bar for attackers AND raised the ceiling for defenders.

The attacker pool grew from thousands to millions. But AI also enables continuous code review, real-time anomaly detection, and vulnerability scanning at every commit. The teams that adopt AI-assisted security first will be the ones who stay ahead.

3

Your security org is one system. Fund it, connect it, hold it accountable as one.

AppSec, IAM, Pen Testing, and Cyber Ops are not four separate teams doing four separate things. Every vulnerability you saw today touches at least two of them. Defence in depth means every layer knows what the others are doing.
