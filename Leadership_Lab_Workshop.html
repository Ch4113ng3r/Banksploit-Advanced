The security mindset

The same feature, read two ways

The price travelled in the receipt. An online shop put each item’s price in a hidden field on the page, so it could show you your total — sensible, and every developer who built it was right. Then someone opened the request, changed price: 4999 to price: 1, and bought a laptop for a pound. Nobody broke in. The shop was simply trusting the shopper to report the price honestly.

Nothing there was a mistake — the vulnerability was a piece of trust nobody noticed they had placed.

A developer hears a reasonable sentence. An attacker hears the same sentence and asks a different question:

What you will hear in the roomWhat an attacker hears
“That field is read-only in the interface.”“Read-only in your browser. I am not using your browser.”
“Only logged-in users can reach that page.”“Logged in as whom — and entitled to see whose data?”
“That library is standard — everyone uses it.”“Including me. I know its default settings better than your team does.”
“We have never had a problem with it.”“That you know of. Nothing here is watching.”

Read those again. Not one of them is wrong, lazy, or unreasonable.

Every one of them is true — and every one is doing the job of a security control without being one.
You do not need to know the answer. You need to notice when a sentence is being used as a safeguard.

Leadership lens: reducing demand for emergency response means disrupting the chain early: secure engineering, identity controls, segmentation, detection and rehearsed recovery.

Why your team keeps asking

“We just patched that. Why again?” Because attention is the vulnerability.

Attention concentrates

One serious flaw marks a product as soft. Researchers — and attackers — pile onto the same code, so a product can sit quiet for years, then produce a cluster of CVEs in weeks. Where one bug surfaces, its siblings are usually next door.

The patch is the map

Publishing a fix shows attackers exactly where the weakness was. They reverse it in hours — and routinely find the fix was incomplete, which becomes the next CVE.

Shared parts, shared pain

Products are built on the same libraries. One flaw in a common component (Log4Shell, OpenSSL) lights up everything that bundles it — at once.

The window has collapsed

A zero-day is exploited before a patch exists. The moment one is disclosed and patched it becomes an N-day — and the race is to apply the fix before attackers weaponise it, now a matter of hours. “Patch now” is the exploitation clock, not drama.

Leadership lens: frequent patching of the same product is not the team overreacting — it is the predictable cost of running a popular, internet-facing target. Patch SLAs and maintenance windows are how you stay ahead of an N-day; and a vendor’s patch quality and track record is itself a risk decision — one you make when you choose a product, and every time you renew it.

When cyber risk becomes business survival

Not every incident closes a company, but some can remove its ability to operate.

Code Spaces

A destructive cloud-account compromise became a widely cited example of a technology business ceasing operations after loss of systems and backups.

NotPetya / Maersk

A trusted software pathway and rapid propagation caused global operational disruption, showing how connected infrastructure amplifies local compromise.

Travelex

A ransomware incident disrupted services and became part of a wider period of financial and operational stress. Avoid claiming cyber was the sole cause of later business outcomes.

Facilitator rule: separate confirmed facts from interpretation. Use “contributed to”, “disrupted” or “amplified” unless a primary source establishes sole causation.

Presenter sources to retain: Maersk annual reporting / public statements; official incident or administrator records where available. Avoid unsupported breach-cost or shutdown claims.

SQL Injection — Login Bypass

📍 /login — Customer ID box

How login normally works

SELECT * FROM users WHERE customer_id = 'BS100234' AND password_md5 = '5f4dcc3b…'

Customer ID and password must match a row — correct, as long as the input is handled as data.

The vulnerable code

// login_vuln.php — Level 0
$sql = "… WHERE customer_id = '" . $cid . "' AND password_md5 = '" . md5($pw) . "'";

$cid is pasted straight into the SQL — whatever you type becomes query logic.

The attack

Enter this as the Customer ID (any password):

BS100234' #
your own Customer ID + ' + #
SELECT * FROM users WHERE customer_id = 'BS100234' #' AND password_md5 = '…' ← commented out, never runs

The ' closes the ID string; # comments out the password check. The database never evaluates the password. We’re in.

This bank's entire authentication just collapsed because of one missing function call.

SQL injection is a 25-year-old vulnerability class.
It's still in the OWASP Top 10.
It's still being written today.

The Fix — And Why It Works

// login_secure.php — parameterized query
$stmt = $pdo->prepare(
    'SELECT id, customer_id, name, role,
            password_hash
       FROM users
       WHERE customer_id = :cid
       LIMIT 1'
);
$stmt->execute([':cid' => $customerId]);

// + password_verify() replaces MD5

Why this works

Step 1: The database receives the SQL template and compiles it into an execution plan. The query structure is locked.

Step 2: User data (:cid) is sent separately and bound to the placeholder as a literal value.

Step 3: The data is never parsed as SQL. Even if the user types ' OR 1=1 #, the database treats the entire string as a value to search for — not as code to execute.

Think of a printed form with blank fields. The form's structure is fixed. Whatever you write in the blanks is content — you can't rewrite the form itself.

Who Should Have Caught This?

Application Security

SAST scanners flag string concatenation in SQL queries automatically. This is one of the most well-known static analysis rules in existence.

Code review catches $pdo->query($sql) with variable interpolation. A single reviewer asking "where does this variable come from?" prevents this vulnerability entirely.

Secure coding standards mandate parameterized queries. The pattern is documented in every language, every framework, every security guide written in the last two decades.

"This is a 25-year-old vulnerability. Automated tools detect it.
The question is: does your SAST pipeline run before merge?"

SQL Injection — Login Bypass

📍 /login — Customer ID box

Goal

Sign in as your own account without knowing the password.

Root cause

Your Customer ID is concatenated straight into the login SQL. A single quote ends the string literal, and everything you type after it is parsed as SQL — so you can rewrite the query's logic and drop the password check.

Level ladder

L0raw query, DB error shown
L1+ blacklist on comments/UNION
L2blind + bracketed + comment filter
L3parameterized + bcrypt

L3 — secure: a parameterized query (customer_id = ?) + password_verify() (bcrypt), one generic “Invalid credentials” message, and a 5-attempt lockout. Input is data, never SQL.

G1

L1 — Naive blacklist

SQL Injection — Login Bypass

The mitigation at this level

Blocks --, #, /* and union (rejects “Illegal characters”). The comment trick now fails — but OR is not blocked.

How to solve it

You can't comment, so make the row match another way. AND binds tighter than OR, so an un-bracketed OR on your Customer ID is enough.

WHERE customer_id = 'BS100234' OR '1'='1'
  AND password_md5 = '…'
reads as:  customer_id='BS100234'  OR  ('1'='1' AND password=…)
            └─ true on its own → row returned

Payload

BS100234' OR '1'='1
no comment needed
G1

L2 — Blind + brackets + comment filter

SQL Injection — Login Bypass

The mitigation at this level

DB error hidden (blind). The Customer ID test is wrapped in ( ) with the password check outside the brackets. Comment tokens are also blacklisted — rejected with a generic “Invalid credentials” (same as a wrong password, so you can't even tell the filter tripped).

How to solve it

A bare OR is now trapped inside the brackets, and you can't comment the tail away. Supply the closing ) yourself to escape the parens, then OR at the top level — the query's own trailing ') balances your quote. No comment.

WHERE (customer_id = 'BS100234') OR ('1'='1')
  AND password_md5 = '…'
reads as:  (customer_id='BS100234')  OR  ('1'='1' AND password=…)
            password branch is false → whole clause = customer_id='BS100234'

Payload

BS100234') OR ('1'='1
close the bracket, OR outside it
💡 Comment-blacklisting is not a SQLi defence — you break the bracket without one.

OTP in the Response Body

📍 OTP screen — browser DevTools

How to find it

1

2

Open DevTools: F12 (Windows) or Cmd+Opt+I (Mac) → Sources / Network.

The OTP is already in your browser — no new request needed.

The attacker’s superpower isn’t hacking — it’s reading what the application is already sending.

What’s in the shipped JavaScript

// otp-validation.js — loaded by the OTP page
var SESSION_DATA = {
  "_t": "otp", "_v": "2.1.4",
  "_otp": "7241",   ← the OTP
  "_flag": "BANKSPLOIT{…}", ← the CTF flag
  "_sid": "abc123", "_exp": 1719500000
};

A developer left debug data in a script shipped to every browser. The OTP — a secret that should live only on the server — is sitting in client-side code.

Client-side code is not secret.

Everything sent to the browser is visible to the user. JavaScript files, hidden form fields, API responses, cookies — all of it is readable.

Secrets belong on the server. Never in JavaScript.

The Fix — Keep the Secret on the Server

// The browser must never receive the OTP,
// nor anything it can be derived from.
$otp = random_int(100000, 999999);
$_SESSION['otp_hash'] = password_hash($otp, PASSWORD_DEFAULT);
$_SESSION['otp_expires'] = time() + 300;

sendSms($user['mobile'], $otp);  // out-of-band only

// On submit — compared server-side:
if (!password_verify($input, $_SESSION['otp_hash'])) {
    recordFailedAttempt();  // + lockout after 5
}

Why this works

The second factor must travel a second channel. If the code arrives in the same response as the page asking for it, it is not a second factor — it is a formality.

Verify server-side. The browser’s job is to collect the input, never to judge it.

Bound attempts and lifetime. A six-digit code with unlimited attempts is a four-minute brute force.

Rule of thumb: open your own site, press Ctrl+U and Ctrl+Shift+I. Anything you can find there, an attacker already has.

Who Should Have Caught This?

Application Security

Nothing sensitive goes to the client. Secrets, internal identifiers, debug objects and verification values must never be serialised into a page or an API response “because the front end needs it.”

Review the response, not just the request. Most review effort goes into validating what comes in. This class of flaw is entirely about what goes out.

Penetration Testing

Automated scanners rarely catch this. The page works perfectly and returns HTTP 200. Finding it requires a human reading the response and asking “why is this here?”

“What does our application send to the browser that it does not actually need to?”

OTP in Response Body

The mitigation at this level

No plaintext OTP. The token id leaks as _seed, the user id as _uid; the flag is sealed in _flag_enc.

How to solve it

Recompute the OTP, then unseal the flag. Inputs are concatenated as strings, not added.

otp = parseInt( sha256(_seed + _uid)[:8], 16) % 10000
then flag = _flag_enc XOR sha256(otp)

Session Puzzling — Walk In Half-Authenticated

“We’re going to skip the second factor entirely — by never finishing the login.”

Login Is Not One Step. It Is a Conversation.

Most banking logins are built in stages. Each stage records something in your session.

Step 1

Password checked.
Session notes who you claim to be.

→
Step 2

OTP sent and verified.

→
Step 3

Session promoted to fully logged in.

→
Dashboard

Your money.

The session is built up piece by piece. The question the attacker asks is simple: what does the application do if I show up at step 4 holding only the piece from step 1?

The Vulnerable Code

Two different variables mean two very different things — and the guard accepts either one.

// Step 1 — after the password is correct
$_SESSION['pending_uid'] = $user['id'];
redirect('/otp');

// Step 2 — only after a valid OTP
$_SESSION['uid'] = $_SESSION['pending_uid'];

pending_uid means “password was right.”
uid means “fully authenticated.”

The guard on every page

// dashboard.php
if (!isset($_SESSION['uid'])
    && !isset($_SESSION['pending_uid'])) {
    redirect('/login');
}
// ... otherwise, show the account ...

That second condition was added so a half-finished login would not look “broken.” It quietly made the OTP optional.

We entered a password, never touched the OTP,
and the bank showed us the account anyway.

Two-factor authentication was fully implemented.
It was simply not required on the page that mattered.

Nobody bypassed the OTP. They just declined to answer it.

The Fix — One State, One Meaning

// Exactly one variable may mean "authenticated".
if (!isset($_SESSION['uid'])) {
    redirect('/login');
}

// On a valid OTP — promote once, cleanly:
session_regenerate_id(true);
$_SESSION['uid'] = $_SESSION['pending_uid'];
unset($_SESSION['pending_uid']);

Why this works

The half-finished state cannot reach anything. There is no longer a condition that accepts it, anywhere.

The intermediate value is destroyed. Once promoted, pending_uid no longer exists to be abused.

The session id is regenerated at the moment privilege changes — which also closes session-fixation attacks.

Note what the fix is not: it is not more code. It is one condition removed and one state deleted.

Who Should Have Caught This?

Identity & Access Management

IAM owns the definition of “authenticated.” If two different variables both look like proof of identity, that is a design gap before it is a coding bug.

One state, one meaning. A partially authenticated session must be structurally incapable of reaching an authenticated page.

Penetration Testing

Static analysis cannot see this. The code is syntactically perfect — the flaw is in the sequence. Only someone deliberately taking steps out of order will find it.

“Which of our checks prove identity, and which only prove that someone started a login?”

📍 /forgot-password · /forgot-password/reset

Goal

Take over another account through the password-recovery flow.

Root cause

The recovery flow writes session state that the authenticated area trusts, without binding progress to the target account. Mixing recovery state and login state in the same session lets one be used to stand in for the other.

Level ladder

L1 / L2progress not bound to the target — swap it in
L3stage bound to the account that earned it

L3 — secure: changing the Customer ID at step 1 clears recovery_stage, and the reset gate requires the stage to have been earned by the same user — recovery_stage_uid === recovery_uid. The swap is refused.

The mitigation at this level

Progress (recovery_stage) is tracked separately from the target (recovery_uid) and isn't bound to it. (L2 currently mirrors L1 — a distinct binding is still to be differentiated.)

$filename — whatever the user sends in the request becomes part of the command line. Shell metacharacters (; | ` $()) break out of the intended command and execute whatever the attacker wants.

The Fix — Two Layers

Primary: Input Validation (Whitelist)

// BEST: only accept safe characters
if (!preg_match(
    '/^[a-zA-Z0-9._-]+$/',
    $filename
)) {
    throw new \InvalidArgumentException(
        'Invalid filename'
    );
}
// Letters, digits, dots, underscores,
// hyphens only — everything else rejected

Define what's allowed, reject everything else. The attack input x.pdf;ls; never reaches the shell — the semicolons fail the whitelist.

Secondary: Shell Escaping (Quick Fix)

// GOOD: escape shell arguments
$cmd = 'wkhtmltopdf '
  . escapeshellarg($src)
  . ' '
  . escapeshellarg($out)
  . ' 2>&1';

escapeshellarg() wraps the value in single quotes and escapes special characters. Good, but relies on the escaping function being bug-free.

Whitelist first. Escape as a safety net. Both together is best.

Who Should Have Caught This?

When Application Security misses a command injection, which other layers should catch it?

🛡️ Cyber Operations / SOC

Should detect unusual process execution — cat, ls, whoami spawned by a web server process is a red flag. Behavioural anomaly detection catches what code review missed.

🏗️ Infrastructure Security

Principle of least privilege. The web process shouldn't have read access to arbitrary files. Container sandboxing, restricted shells, and process isolation limit blast radius.

"Security is layers. When one fails, the next should catch it."

Goal

Run OS commands as www-data (RCE) and read the flag file.

Root cause

The Download-PDF control shells out to wkhtmltopdf with your output filename unescaped. Shell metacharacters in the filename start new commands. (Runs in an emulated honeypot shell — no real host access, no egress.)

Note. The flag file is per-user: /tmp/flag_g9_<id>.txt. id → uid=33(www-data); ls /tmp finds the filename.

Level ladder

L0raw — ';' chains commands
L1blacklist ; & — use the pipe
L2blacklist ; & | + spaces — newline + $IFS
L3escapeshellarg() on every arg

L3 — secure: escapeshellarg() wraps every argument, so ;, |, newline and $IFS are all treated as literal filename characters — a real PDF is returned and nothing breaks out.

AI in Security

The Accelerant

AI as Attacker

Everything demonstrated in this session — the SQL injection payloads, the JWT forgery, the IDOR patterns, the command injection — an AI model can generate all of it from a single prompt.

What AI Can Do Today

Generate SQL injection payloads tailored to any login form. Craft JWT forgeries given a sample token. Enumerate IDOR patterns from API documentation. Write brute-force scripts in any language, in seconds.

What This Means

AI can lower the skill and time required to attempt familiar attacks, but successful exploitation still depends on access, context, validation and operational skill. The practical implication is greater attack volume and faster iteration.

The Bar Has Dropped to Zero

Prompt:

"Generate SQL injection payloads to bypass a login form that checks customer_id and password"

AI Output:

BS100234' #                // Comment out password check
' OR 1=1 #                  // Tautology bypass
' UNION SELECT 1,2,3,4 #    // Column enumeration
admin'/*                       // Block comment variant

AI can accelerate payload design and testing, but its output must be authorised, validated and constrained. It does not remove the need for technical expertise.

AI as Defender

The same AI capabilities that enable attacks also power defence at unprecedented speed and scale.

SAST / DAST with AI

AI-assisted analysis can flag suspicious injection patterns, unsafe APIs, exposed client-side data and risky configurations. Business-logic and authorisation findings still require context and validation.

AI Code Review

Identifies client-trust anti-patterns, reviews pull requests for security regressions, suggests fixes with correct code. Scales security review to every commit, not just the ones a human has time to read.

Anomaly Detection

AI-based SOC tools flag unusual command execution from web processes, detect brute-force patterns across login endpoints, identify bulk data extraction from statement APIs.

Pen Test Triage

Prioritises findings by exploitability and business impact. Maps vulnerabilities to OWASP categories and CWEs automatically. Reduces triage time from days to hours.

AI Accelerates Both Sides Equally

Attackers

Lower barrier to entry. Automated payload generation. Faster reconnaissance. Wider target surface. Anyone with a prompt can attempt what once required years of expertise.

Defenders

Automated vulnerability detection. Continuous code review at scale. Real-time anomaly detection. Faster incident triage. Security testing on every commit, not just quarterly pen tests.

The difference is who adopts it first and uses it consistently.

What AI Still Cannot Do

AI is a powerful tool, but these require a human in the loop — today and for the foreseeable future.

🧠 Business Context

AI can flag a missing auth check but can't know if that page is intentionally public. Understanding the business requirement behind code is a human judgment call.

⚖️ Risk Acceptance Decisions

"We accept this risk for 90 days with compensating controls" — weighing business priorities, regulatory exposure, and customer trust. No model can own that decision.

🔍 Validating AI Output

AI hallucinates — it generates confident, plausible, and completely wrong security advice. Every AI recommendation must be validated by someone who knows the domain.

🚨 The 2 AM Judgment Call

When the alert fires: escalate or contain? Notify the regulator now or investigate first? Shut down the service or accept partial risk? Human decisions with human consequences.

🤝 Stakeholder Negotiation

Convincing a product team to delay a launch for a critical fix. Explaining risk to the board in non-technical language. AI can draft the memo — but can't have the conversation.

🏗️ Culture Building

Making developers want to write secure code. Creating an environment where reporting vulnerabilities is rewarded, not punished. Culture comes from leaders, not algorithms.

AI is a force multiplier for your security teams, not a replacement.

AI can find the SQL injection in milliseconds. But a human decided to skip the code review that would have caught it. AI can detect the brute-force in real time. But a human decided not to fund the SOC tooling.

It still takes a human to decide that security matters.

To respond when the alert fires at 2 AM.

When a High-Risk Finding Lands on Your Desk

Before raising an ORAC (Operational Risk Acceptance Certificate), ask these questions:

🛡️ Compensating Controls

"If we can't fix it now, what reduces the risk?"
WAF rules for injection, enhanced logging for IDOR, network segmentation for command injection, rate limiting for brute force.

📅 Fix Timeline

"What is the hard deadline to remediate?"
Risk acceptance without a fix date is risk ignorance. Set a date. Track it. Escalate if it slips.

💥 Exploitation Impact

"If this is exploited tomorrow, what's the blast radius?"
Financial loss? Regulatory penalty? Reputational damage? Customer data exposed? Quantify — don't guess.

🔍 Validation

"Has Pen Testing confirmed this is exploitable? Can SOC detect exploitation?"
Ask the security team to prove the risk. Then ask if monitoring can catch it live.

Risk acceptance is not risk ignorance.
Accept with controls, timelines, and accountability.
