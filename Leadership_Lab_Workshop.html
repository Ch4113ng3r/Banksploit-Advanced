The security mindset

The same feature, read two ways

The price travelled in the receipt. An online shop put each item’s price in a hidden field on the page, so it could show you your total — sensible, and every developer who built it was right. Then someone opened the request, changed price: 4999 to price: 1, and bought a laptop for a pound. Nobody broke in. The shop was simply trusting the shopper to report the price honestly.

Nothing there was a mistake — the vulnerability was a piece of trust nobody noticed they had placed.

Why your team keeps asking

“We just patched that. Why again?” Because attention is the vulnerability.

Attention concentrates

One serious flaw marks a product as soft. Researchers — and attackers — pile onto the same code, so a product can sit quiet for years, then produce a cluster of CVEs in weeks. Where one bug surfaces, its siblings are usually next door.

The patch is the map

Publishing a fix shows attackers exactly where the weakness was. They reverse it in hours — and routinely find the fix was incomplete, which becomes the next CVE.

Shared parts, shared pain

Products are built on the same libraries. One flaw in a common component (Log4Shell, OpenSSL) lights up everything that bundles it — at once.

The window has collapsed

A zero-day is exploited before a patch exists. The moment one is disclosed and patched it becomes an N-day — and the race is to apply the fix before attackers weaponise it, now a matter of hours. “Patch now” is the exploitation clock, not drama.

Leadership lens: frequent patching of the same product is not the team overreacting — it is the predictable cost of running a popular, internet-facing target. Patch SLAs and maintenance windows are how you stay ahead of an N-day; and a vendor’s patch quality and track record is itself a risk decision — one you make when you choose a product, and every time you renew it.

SQL Injection — Login Bypass

📍 /login — Customer ID box

How login normally works

SELECT * FROM users WHERE customer_id = 'BS100234' AND password_md5 = '5f4dcc3b…'

Customer ID and password must match a row — correct, as long as the input is handled as data.

The vulnerable code

// login_vuln.php — Level 0
$sql = "… WHERE customer_id = '" . $cid . "' AND password_md5 = '" . md5($pw) . "'";

$cid is pasted straight into the SQL — whatever you type becomes query logic.

The attack

Enter this as the Customer ID (any password):

BS100234' #
your own Customer ID + ' + #
SELECT * FROM users WHERE customer_id = 'BS100234' #' AND password_md5 = '…' ← commented out, never runs

The ' closes the ID string; # comments out the password check. The database never evaluates the password. We’re in.

This bank's entire authentication just collapsed because of one missing function call.

SQL injection is a 25-year-old vulnerability class.
It's still in the OWASP Top 10.
It's still being written today.

The Fix — And Why It Works

// login_secure.php — parameterized query
$stmt = $pdo->prepare(
    'SELECT id, customer_id, name, role,
            password_hash
       FROM users
       WHERE customer_id = :cid
       LIMIT 1'
);
$stmt->execute([':cid' => $customerId]);

// + password_verify() replaces MD5

Why this works

Step 1: The database receives the SQL template and compiles it into an execution plan. The query structure is locked.

Step 2: User data (:cid) is sent separately and bound to the placeholder as a literal value.

Step 3: The data is never parsed as SQL. Even if the user types ' OR 1=1 #, the database treats the entire string as a value to search for — not as code to execute.

Think of a printed form with blank fields. The form's structure is fixed. Whatever you write in the blanks is content — you can't rewrite the form itself.

Who Should Have Caught This?

Application Security

SAST scanners flag string concatenation in SQL queries automatically. This is one of the most well-known static analysis rules in existence.

Code review catches $pdo->query($sql) with variable interpolation. A single reviewer asking "where does this variable come from?" prevents this vulnerability entirely.

Secure coding standards mandate parameterized queries. The pattern is documented in every language, every framework, every security guide written in the last two decades.

Root cause

Your Customer ID is concatenated straight into the login SQL. A single quote ends the string literal, and everything you type after it is parsed as SQL — so you can rewrite the query's logic and drop the password check.

Level ladder

L2blind + bracketed + comment filter
L3parameterized + bcrypt

The mitigation at this level

Blocks --, #, /* and union (rejects “Illegal characters”). The comment trick now fails — but OR is not blocked.

How to solve it

You can't comment, so make the row match another way. AND binds tighter than OR, so an un-bracketed OR on your Customer ID is enough.

  AND password_md5 = '…'
reads as:  customer_id='BS100234'  OR  ('1'='1' AND password=…)
            └─ true on its own → row returned

no comment needed

// otp-validation.js — loaded by the OTP page

  "_t": "otp", "_v": "2.1.4",

A developer left debug data in a script shipped to every browser. The OTP — a secret that should live only on the server — is sitting in client-side code.

Client-side code is not secret.

Everything sent to the browser is visible to the user. JavaScript files, hidden form fields, API responses, cookies — all of it is readable.

Secrets belong on the server. Never in JavaScript.

💡 Security MindsetL11 • OTP in the response body

If the browser can see it, it isn’t a secret.

A private OTP was included in data sent to the browser — where users can inspect responses, scripts and client-side logic.

01  The assumption

Debugging data was safe to leave in the client.

• A value added for development or testing, not removed before production.

• The team assumed hiding, encoding or hashing it made it safe to ship.

• The browser was treated as trusted, though its contents are visible to the user.

02  Ask your team

What are we exposing—and why?

• Is any debug data, test logic, OTP, token or secret reaching production browsers?

• Are we using hashing or encoding to protect a value that should never leave the server?

• If a user can inspect or guess the value, can they recover, replay or use it to bypass verification?

03  The leadership response

Make production exposure difficult to miss.

• Keep OTPs and security-critical secrets server-side; send the browser only what it needs.

• Use production-build controls, code review and scans to catch debug artefacts and sensitive data.

• Treat hashes of low-entropy values (e.g. short OTPs) as guessable — not automatically secret.

Why leaders should care

A debug oversight or false sense of protection can undermine OTP verification and risk unauthorised account access.

Mindset shift  “We hid or hashed it” → “Why is this secret reaching the client at all?”

💡 Security MindsetL25 • Session puzzling

The feature worked. The trust model didn’t.

A forgot-password flow can contain valid controls—and still be exploitable when the application trusts workflow progress more than verified identity.

01  The assumption

• A completed step is treated as proof that the right person completed it for the right account.

• Users are expected to follow the intended sequence; session progress is trusted without enough re-validation.

• Secure components (passwords, OTPs, sessions) are mistaken for a secure end-to-end process.

02  The attacker’s question

• Can I skip, repeat, reorder or manipulate a step?

• Can I change the account being recovered while retaining progress earned elsewhere?

• Can I reach a sensitive action without proving the required identity and authority again?

03  The leadership response

• Bind every verification step to the exact account and re-check it at each sensitive action.

• Test complete business journeys—not just individual controls or happy paths.

• Ask teams to challenge assumptions and explore misuse, abuse and unintended behaviour.

Why leaders should care

One weakness in a recovery workflow can become account takeover—putting customer trust, data, financial assets and reputation at risk.

Mindset shift  “Does it work as intended?” → “How could someone make it work in a way we never intended?”

Across these demos, the pattern was consistent: the application trusted something it should have verified.

01   Identity ≠ authorisation

A logged-in user is not automatically entitled to every account or record.

ASK  Do we verify ownership and permission for the exact object at every sensitive action?

EXPECT  Server-side, per-object authorisation checks; test with two distinct customer identities.

02   The client is not trusted

Anything sent to the browser can be inspected, copied or manipulated.

ASK  Are secrets, OTPs, debug values or security decisions reaching the client?

EXPECT  Keep secrets and security-critical decisions server-side; inspect shipped scripts and responses.

03   Input must remain data

User-controlled input must never change the instructions our systems execute.

ASK  Are we relying on filters — or structurally preventing input from changing a query?

EXPECT  Use parameterised queries; validate business rules; test hostile input on sensitive paths.

04   Workflows must be challenged

A feature can work correctly and still fail when steps, state or trust are manipulated.

ASK  Do we test only the happy path, or also skipped, repeated, reordered and abused journeys?

EXPECT  Threat-model end-to-end flows; test session transitions, recovery paths and negative scenarios.

"If we can't fix it now, what reduces the risk?"
WAF rules for injection, enhanced logging for IDOR, network segmentation for command injection, rate limiting for brute force.

📅 Fix Timeline

"What is the hard deadline to remediate?"
Risk acceptance without a fix date is risk ignorance. Set a date. Track it. Escalate if it slips.

💥 Exploitation Impact

"If this is exploited tomorrow, what's the blast radius?"
Financial loss? Regulatory penalty? Reputational damage? Customer data exposed? Quantify — don't guess.

🔍 Validation

"Has Pen Testing confirmed this is exploitable? Can SOC detect exploitation?"
Ask the security team to prove the risk. Then ask if monitoring can catch it live.
